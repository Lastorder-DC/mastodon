# OCCM Groups feature specification and migration plan

Two documentation files define a private, local-only groups feature for this Mastodon fork: a 1,885-line feature spec covering schema, API, permissions, streaming, notifications, UI, and i18n; and a 916-line migration/rollback plan for transitioning to the official PR #19059 implementation if it ships. The main risks are in the security boundaries between group-internal moderation and server-level moderation, the `limited` visibility reuse for group posts, and several under-specified behavioral edge cases that will surface during implementation.

**Watch for:** Reuse of `limited` visibility creates an ambiguity with circle posts that the spec doesn't resolve (confirmed). The report system is entirely invisible to server admins, creating a blind spot for illegal content (confirmed). The `member_count` counter cache has no documented reconciliation mechanism (confirmed). The migration plan hardcodes a visibility integer (`GROUP_VISIBILITY = 5`) that doesn't exist yet and could be wrong (confirmed).

## High-level view

The single-admin constraint is enforced only at the application level (service objects and policies) rather than at the database level, which leaves room for data inconsistency under concurrent requests or raw SQL operations.

The spec defines some endpoints inconsistently between sections (e.g., Section 3.2 uses `POST /members` for joining while Section 6.3's rollback routes reference `POST /join`), and never specifies pagination parameters for membership and report list endpoints.

The non-federation guarantee relies on `visibility: :limited` plus the `local_only: true` flag passed to `PostStatusService`. The `limited` visibility integer (4) is already used by Mastodon for circle posts, so group posts become indistinguishable from other limited-visibility statuses without joining through the `occm_group_statuses` junction table. This has implications for any code path that filters on `visibility = 4`.

The migration plan's main weakness is the assumption that PR #19059's schema will match the snapshot described here. The hardcoded `GROUP_VISIBILITY = 5` constant and the assumed `group_membership_requests` table could easily diverge from what actually ships.

The streaming design publishes group updates to every active member's home feed via `FeedManager.instance.push_to_home`, contradicting Section 11.4 which explicitly states group posts "only appear in the group timeline, never in home/public/hashtag timelines."

1. **Home feed contradiction** — `DistributeOccmGroupStatusService` calls `push_to_home` for every member, but Section 11.4 says group posts never appear in the home timeline. Remove the `push_to_home` call or revise the visibility rules.

5. **Hardcoded migration visibility constant** — `GROUP_VISIBILITY = 5` is a guess. Replace with a lookup against the actual enum at migration time, or add a pre-migration assertion.
6. **Route inconsistency** — Section 3.2 defines `POST /members` for joining, but the rollback routes in Section 6.3 reference `POST /join` and `POST /leave`. Unify.
7. **Missing pagination on members/reports** — Member list and report list endpoints don't specify pagination parameters or max page size. For large groups this will be a performance problem.
8. **`occm_group_status` N+1 in serializer** — `REST::OccmGroupSerializer#membership` issues a query per group in list views. Preload memberships in the controller's `index` action.

## Home feed vs. group-only timeline contradiction

Section 11.4 states: "Group posts only appear in the group timeline, never in home/public/hashtag timelines." Section 12.3's `DistributeOccmGroupStatusService` does the opposite:

```ruby
occm_group.occm_group_memberships.active.pluck(:account_id).each do |account_id|
  FeedManager.instance.push_to_home(Account.find(account_id), status)
end
```

This pushes every group post into every member's home feed. It also issues an `Account.find` per member inside a loop, which is an N+1 on top of the semantic contradiction. If the intent is group-timeline-only, the distribution service should only publish to the Redis streaming channel and not touch home feeds. If the intent is to surface group posts in home, Section 11.4 needs correcting.

## `limited` visibility reuse and status discrimination

Mastodon uses `limited` (integer 4) for circle posts and other constrained-audience statuses. The spec assigns the same value to group posts, creating an ambiguity: any code that queries `WHERE visibility = 4` will return both circle posts and group posts. The `occm_group_statuses` junction table provides the discriminator, but the spec never documents a join or scope that must be applied across Mastodon's existing status-filtering code paths (home feed fanout, account timeline, search, notifications).

In the migration plan, this becomes even more visible: converting from `limited` to a new `group` visibility requires targeting only statuses that exist in `occm_group_statuses`, not all limited-visibility statuses. The plan handles this correctly, but the feature spec should document the invariant during normal operation.

## Server-admin moderation blind spot

Section 7.1 states: "Group reports are handled entirely by the group's admin and moderators. They do NOT appear in the server admin interface." This creates a gap for content that requires server-level intervention (illegal content, court orders, terms-of-service violations that affect the instance's reputation).

The spec should define an escalation path. Options: (a) server admins can always view group content via the existing admin API, (b) group reports can be escalated to server-level reports by group moderators, (c) automated detection rules (e.g., media scanning) still apply to group posts since they're stored in the `statuses` table. Without this, an operator running the fork has no visibility into group content.

## Counter cache without reconciliation

`occm_groups.member_count` is incremented/decremented by service objects (implied by the spec's service layer). If a membership record is deleted by cascade (e.g., account deletion triggers `ON DELETE CASCADE` on `occm_group_memberships`), the counter cache is not decremented because no Rails callback fires. Mastodon handles this for followers via periodic reconciliation workers. The spec should document a similar mechanism or accept eventual inconsistency.

## Migration plan: hardcoded visibility constant

```ruby
GROUP_VISIBILITY = 5 # PR #19059 "group" visibility value (verify actual value)
```

The comment acknowledges uncertainty. If the actual value differs when PR #19059 ships, the migration silently writes incorrect visibility values to production statuses. The migration should either derive the value from the enum definition at runtime (`Status.visibilities['group']`) or include a pre-flight assertion that aborts if the expected value doesn't match.

## Route definition inconsistency

The main spec (Section 3.2) defines the join action as `POST /api/v1/occm_groups/:group_id/members` (creating a membership resource). The rollback section (migration plan Section 6.3) references `post :join` and `post :leave` as member routes. These represent two different URL designs for the same operation. The implementation will follow one pattern; the other section will be stale.

## Serializer N+1 query risk

```ruby
def membership
  @membership ||= object.occm_group_memberships.find_by(account_id: current_user&.account_id)
end
```

In `index` actions that render multiple groups, this fires one query per group. The controller should preload the current user's memberships via a single query scoped to the returned group IDs.

## Missing behavioral details worth specifying before implementation

Edge cases unaddressed by the spec:

- What happens when a blocked user tries to join a group owned by the blocker (or vice versa)?
- Can a suspended account's group continue to function, or does suspension cascade to group deletion?
- Is there a rate limit on join requests to prevent spam-joining many groups?
- What happens to a group's statuses when the group is deleted? Are they destroyed (via `dependent: :destroy` on `occm_group_statuses`), or do they become orphaned limited-visibility posts?
- The `rejected` membership state is stored permanently. Is there a mechanism to re-request after rejection, or is rejection permanent?

These will become implementation ambiguities if not resolved before coding begins.
