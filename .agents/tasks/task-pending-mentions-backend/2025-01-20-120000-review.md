# Redis-backed pending mentions cache with dismiss button

A new "pending mentions" feature stores unresolved mention notifications in a Redis sorted set (`pending_mentions:{account_id}`) and exposes them through a dedicated REST API (`GET/DELETE /api/v1/pending_mentions`). The frontend is rewired from client-side notification filtering to server-side fetching, and gains a dismiss (X) button on each item. NotifyService adds mentions on arrival; FavouriteService and PostStatusService remove them on favourite or reply.

**Watch for:** Cache-vs-notification desync when notifications are deleted or cleared via existing endpoints (confirmed). The `populate` method runs N+2 queries per notification inside a request cycle with no background offloading (confirmed). No TTL on the Redis key means orphaned entries persist indefinitely (confirmed).

## High-level view

The Redis cache uses the same sorted-set-with-notification-id-as-score pattern as Mastodon's feed infrastructure, giving constant-time add/remove and cursor-based pagination. But the cache has no awareness of notification lifecycle events outside the three hooks added here — a user who clears all notifications or blocks an account will retain stale entries in the pending set until the next `populate` call (which itself only triggers when the set is completely empty).

The `populate` method issues per-notification queries for `Favourite.exists?` and `Status.exists?` inside a loop capped at 800 iterations. On first access this runs synchronously in the request thread, blocking the API response with potentially hundreds of database round-trips.

The frontend reducer stores full `ApiNotificationJSON` objects rather than normalized IDs, doubling memory usage for statuses shown in this view compared to how `notification_groups` handles it.

1. **Stale cache on notification clear/dismiss/block** — When notifications are destroyed via `NotificationsController#clear`, `#dismiss`, or `AfterBlockService`, their IDs remain in the pending mentions Redis set. Add a hook (or use a callback/concern on `Notification#destroy`) to remove from `PendingMentionCache` when a mention notification is deleted.
2. **Populate N+1 in request thread** — `PendingMentionCache.populate` runs up to 800 `Favourite.exists?` + `Status.exists?` queries synchronously during `GET /api/v1/pending_mentions`. Move population to a Sidekiq worker or batch the existence checks with `WHERE id IN (...)` queries.
3. **No TTL on Redis keys** — The sorted set has no expiration. If an account is deleted or goes dormant, the key persists in Redis forever. Set a TTL (e.g., 30 days) and refresh it on write, or hook into account cleanup.
4. **Populate race condition** — `populate_if_empty!` checks `count == 0` then populates. Two concurrent requests hitting an empty set will both populate, potentially doubling database load. Use a Redis lock or `SETNX`-based guard.
5. **Frontend stores full notification JSON** — The reducer retains complete `ApiNotificationJSON` objects (including full status bodies) rather than storing only IDs and reading from the normalized store. This diverges from the `notification_groups` pattern and doubles memory for statuses in this view.

## Cache lifecycle gaps

The cache is updated via three hooks: `NotifyService` (add), `FavouriteService` (remove), `PostStatusService` (remove on reply). But notification deletion — through `NotificationsController#dismiss`, `#clear`, `AfterBlockService`, or `AfterBlockDomainFromAccountService` — bypasses the cache entirely. A dismissed or cleared notification leaves a dangling ID in the sorted set. When the controller later queries `Notification.where(id: notification_ids)`, it won't find the record, so the entry disappears from the API response but still occupies space in Redis and pollutes pagination cursors.

The `populate_if_empty!` guard only re-scans when `zcard == 0`. A single stale entry prevents repopulation indefinitely. The user has no way to force a cache rebuild short of manually dismissing every visible item until the set empties.

A targeted fix: hook into `Notification` after-destroy (or a concern) to call `PendingMentionCache.remove` when the notification type is `:mention`. A broader fix: set a TTL on the key (e.g., 30 days, refreshed on each write) so that stale sets eventually self-heal.

## Populate performance

```ruby
notifications.each do |notification|
  status = notification.target_status
  next if status.nil?
  next if Favourite.exists?(account: account, status: status)
  next if Status.exists?(account: account, in_reply_to_id: status.id)
  add(account_id, notification.id)
end
```

For 800 notifications, this issues up to 1600 SQL queries. This runs inside the `index` action, making the first page load extremely slow for users with many mention notifications. The Mastodon pattern for heavy work like this is a Sidekiq worker — `FeedManager` populates feeds via `RegenerationWorker`, not inline. The controller could enqueue the worker, return an empty list, and let subsequent requests read from the populated set.

Even without a worker, the queries can be batched: collect all status IDs, then do `Favourite.where(account: account, status_id: status_ids).pluck(:status_id)` and `Status.where(account: account, in_reply_to_id: status_ids).pluck(:in_reply_to_id)` — two queries total instead of 1600.

## Populate race condition

```ruby
def populate_if_empty!
  return unless PendingMentionCache.count(current_account.id).zero?
  PendingMentionCache.populate(current_account.id)
end
```

Two concurrent requests for the same user (e.g., browser + mobile) both see `count == 0`, both run `populate`, and each calls `zadd` for every qualifying notification. `zadd` is idempotent so data isn't corrupted, but the duplicate work doubles the database load during an already-expensive operation. A Redis `SET NX` on a lock key with a short TTL would prevent the second caller from re-populating.
