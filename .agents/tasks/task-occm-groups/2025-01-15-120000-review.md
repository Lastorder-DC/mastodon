# OCCM Groups: private group messaging for Mastodon

A full-stack private groups feature: members-only timeline, approval-based join flow, group moderation (reports, role promotion, member removal), real-time streaming, and a React frontend with navigation integration. Posts use `limited` visibility and bypass the normal fan-out pipeline, publishing only through a group-specific Redis channel. The design mirrors Mastodon's existing List infrastructure extended with role-based access control.

**Watch for:** The frontend timeline fetcher points at the wrong API endpoint (confirmed). The serializer can't resolve the viewer's role/state on single-group endpoints (confirmed). The member removal endpoint has no authorization gate — any active member can remove any other non-admin member (confirmed).

## High-level view

The data model is five tables: groups, memberships, statuses, reports, and DM rooms (DM rooms are schema-only with no service logic yet). Memberships carry an integer enum for both role (admin/moderator/user) and state (pending/active/rejected), with a composite unique index on (group, account). The design supports approval-required groups and open-join groups via a single boolean flag.

Posts flow through `PostToOccmGroupService`, which delegates to `PostStatusService` with `visibility: :limited, local_only: true`, then creates an `OccmGroupStatus` join record and publishes via `DistributeOccmGroupStatusService`. The normal `FanOutOnWriteService` short-circuits when it detects a group post. Visibility enforcement is retrofitted into `StatusPolicy` and `AccountStatusesFilter`.

The streaming server adds an `occm_group` channel with a Postgres-backed membership check at subscription time. The Node.js integration follows the established `list` channel pattern, but there is no ongoing membership validation after the initial connect — if a member is removed mid-session, they continue receiving events until they reconnect.

The frontend uses an Immutable.js-based reducer, thunk-style actions, and six route-level components (listing, timeline, create/edit, members, reports). The timeline component connects the streaming channel and uses `expandTimeline` for pagination, but its API path does not match the backend route.

1. **Timeline endpoint mismatch** — Frontend fetches `/api/v1/occm_groups/:id/statuses` for timeline pagination, but the backend timeline is at `/api/v1/occm_groups/:id/timeline`. Change `expandOccmGroupTimeline` and `fillOccmGroupTimelineGaps` to use `/api/v1/occm_groups/${id}/timeline`.
2. **Serializer missing `current_account`** — `OccmGroupSerializer#membership` falls back to `instance_options[:current_account]` for `show`/`create`/`update`/`transfer`, but no controller passes it. `role` and `membership_state` will always be null outside the index action. Pass `current_account: current_account` in render options.
3. **Member removal lacks authorization** — `MembersController#destroy` requires only active membership, not moderation role. Any member can remove any other non-admin member. Add `authorize @occm_group, :moderate?` or scope self-removal separately.
4. **`leaveOccmGroup` passes `'me'` as account_id** — The frontend calls `DELETE /members/me` but the service does `find_by!(account_id: 'me')` against a bigint column, which will raise a type error or 404. Resolve `'me'` to `current_account.id` in the controller before calling the service.
5. **N+1 in `StatusPolicy#occm_group_post?`** — Each status visibility check runs `OccmGroupStatus.exists?(status_id: record.id)`, adding a query per status in any timeline render that calls `show?`. Preload or cache group-status existence.
6. **No streaming disconnect on removal** — When a member is removed, `RemoveOccmGroupMemberService` publishes a `remove_member` event but the streaming server never forces a channel unsubscribe. The removed member continues receiving updates until they reconnect.
7. **Counter non-atomicity** — `increment!` and `decrement!` on `member_count` without database-level locking can drift under concurrent joins/removals. The reconciliation worker mitigates this but doesn't eliminate the window.

## Timeline endpoint path mismatch

The backend defines two distinct resources under each group: `resources :statuses, only: [:create, :destroy]` for posting/deleting, and `resource :timeline, only: [:show]` for reading the feed. The timeline controller lives at `Api::V1::OccmGroups::TimelinesController#show` and responds to `GET /api/v1/occm_groups/:id/timeline`.

The frontend's `expandOccmGroupTimeline` in `actions/timelines.js` targets `/api/v1/occm_groups/${id}/statuses` — this is the statuses resource (POST/DELETE only, no GET). A GET request to that path will return a 404 or routing error. The same error applies to `fillOccmGroupTimelineGaps`. The streaming connection is separate and will work, but paginated loads and initial timeline fetch are broken.

## Serializer context gap

`REST::OccmGroupSerializer` computes `role` and `membership_state` by looking up the current viewer's membership. In the `index` action, this is handled via a pre-fetched `memberships_map` keyed by group ID — efficient and correct. In all other actions (`show`, `create`, `update`, `transfer`), neither `memberships_map` nor `current_account` is provided in instance options. The fallback path runs:

```ruby
object.occm_group_memberships.find_by(account: instance_options[:current_account])
```

With `instance_options[:current_account]` being nil, this always returns nil, so `role` and `membership_state` serialize as null. The frontend `OccmGroupTimeline` component reads `group.get('role')` to decide whether to show edit/member links — these will never appear after navigating to a single group.

## Authorization gap in member removal

`MembersController#destroy` calls `RemoveOccmGroupMemberService.new.call(@occm_group, params[:id], current_account)`. The `before_action :require_active_membership!` ensures the caller is a member, but nothing checks whether they have moderation rights. The service itself only blocks removing admins:

```ruby
raise Mastodon::ValidationError if @membership.role_admin?
```

This means any active user-role member can remove any other user-role member by sending `DELETE /api/v1/occm_groups/:group_id/members/:other_account_id`. The intended behavior is likely that only moderators/admins can remove others, while any member can remove themselves (leave). The controller needs to differentiate self-removal from moderation-removal.

## `leaveOccmGroup` sends `'me'` as account_id

The frontend action dispatches:

```typescript
apiRemoveOccmGroupMember(groupId, 'me');
```

This hits `DELETE /api/v1/occm_groups/:group_id/members/me`. The controller passes `params[:id]` (the string `"me"`) to `RemoveOccmGroupMemberService`, which runs:

```ruby
@group.occm_group_memberships.where(state: :active).find_by!(account_id: account_id)
```

PostgreSQL will reject casting `'me'` to bigint, raising an `ActiveRecord::StatementInvalid`. The controller should intercept this case and resolve to `current_account.id` before delegation.

## N+1 query in StatusPolicy

`StatusPolicy#occm_group_post?` runs:

```ruby
record.limited_visibility? && OccmGroupStatus.exists?(status_id: record.id)
```

This is called for every status rendered in any timeline (home, public, account). For a 40-status page, that's up to 40 additional `SELECT 1 FROM occm_group_statuses WHERE status_id = ?` queries, all for statuses that likely aren't group posts. Since `Status` now `has_one :occm_group_status`, the check could use the preloaded association (`record.occm_group_status.present?`) if `occm_group_status` is included in `CACHEABLE_ASSOCIATIONS`.

Additionally, `viewable_for_occm_group?` runs two more queries (find the `OccmGroupStatus`, then check membership). Both hit cold paths for non-group statuses, but the exists-check overhead remains.

## Streaming server membership check is connect-time only

The `authorizeOccmGroupAccess` function queries the database for an active membership row before allowing the WebSocket subscription:

```javascript
const result = await pgPool.query(
  'SELECT id FROM occm_group_memberships WHERE occm_group_id = $1 AND account_id = $2 AND state = 1 LIMIT 1',
  [groupId, accountId],
);
```

After this check passes, the subscription persists indefinitely. When `RemoveOccmGroupMemberService` fires, it publishes a `remove_member` event to the channel, but the streaming server never processes this as a forced disconnect. The removed member's client receives the event (which the frontend doesn't handle) and continues receiving all subsequent group updates until the connection drops. This is a privacy concern for groups with sensitive content.

## Counter management

`member_count` is updated via `increment!`/`decrement!` without row-level locking. Under concurrent approve/remove operations, the counter can drift. The `OccmGroupCounterReconciliationWorker` fixes this by scanning all groups periodically, but it has no scheduling configuration in this diff (no `config/sidekiq.yml` entry, no `whenever` cron). It relies on being called externally.

The `TransferOccmGroupAdminService` properly uses `@group.lock!` inside a transaction for role swaps — that pattern is not applied to membership count mutations.

## DM Rooms table without implementation

The `occm_group_dm_rooms` migration creates a table and the model has validations, but no controller, service, or frontend component references it. This is dead schema that will need a migration to drop if the feature is abandoned, or additional implementation if intended for future use.

## Test coverage gaps

The test suite covers the primary happy paths: CRUD, join flows, approve/reject, removal, reports, and timelines. Service specs mock `NotifyOccmGroupService` to avoid side effects.

Not tested:

- `StatusPolicy` changes (group post visibility enforcement)
- `AccountStatusesFilter` exclusion of group posts
- `FanOutOnWriteService` short-circuit for group posts
- `DeleteOccmGroupStatusService` (no spec exists)
- `DistributeOccmGroupStatusService` (no spec exists)
- `ResolveOccmGroupReportService` resolution actions (the spec mocks the entire service)
- Streaming server authorization and channel routing
- `OccmGroupCounterReconciliationWorker`
- Notification delivery end-to-end (all specs mock the notify service)
- `OccmGroupPolicy` (no dedicated policy spec)
- Frontend components (no JS test files)
