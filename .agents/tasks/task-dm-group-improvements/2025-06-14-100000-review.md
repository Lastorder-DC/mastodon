# Group DM improvements: unread counters, batch member add, avatar badge, vacuum fix

This change converts DM read receipts from a binary "Read" indicator into a numeric unread counter (KakaoTalk-style), where each message shows how many group members haven't read it yet. It also fixes the member-add controller to accept an `account_ids` array (eliminating a 404 when the frontend sends multiple IDs), adds a participant-count badge on group chat avatars in the chat list, and excludes DM attachments from the orphan media vacuum.

**Watch for:** The batch member-add endpoint has no upper bound on array size (confirmed), which enables a single request to trigger unbounded sequential DB lookups. The unread count calculation iterates all read receipts for every rendered message (confirmed), which may become expensive in large groups with long message histories.

## High-level view

The read receipt system shifts from a boolean per-message ("has anyone read this?") to a count ("how many people haven't read this?"). The calculation derives the count from `totalOtherMembers - readCount`, using the current `participant_ids.length` as the total. This means the count reflects current membership, not membership at send time — if someone joins later, existing messages will retroactively show a higher unread count until that new member catches up.

The member-add controller now loops over an array of account IDs, calling `Account.find` and the block-check independently for each. There's no transaction wrapping the loop, so a failure partway through (e.g., second account is blocked) leaves earlier memberships committed. There's also no limit on array size, so an attacker could send thousands of IDs in one request.

The media vacuum exclusion is a one-line `NOT IN` subquery that prevents DM attachments from being garbage-collected as orphans. If `DmMessageAttachment` grows to millions of rows, this subquery could become a performance bottleneck for the vacuum job.

<summary>Issues (4)</summary>

1. **No cap on account_ids array size** (confirmed) — The member-add endpoint accepts an unbounded array and does N sequential `Account.find` + block-check queries with no limit. Add a size cap (e.g., 20) and reject requests exceeding it.
2. **Partial commit on batch member-add failure** (confirmed) — The loop isn't wrapped in a transaction; if the 3rd account is blocked, the first two memberships are already committed. Wrap the loop in `ActiveRecord::Base.transaction`.
3. **Unread count inflated by late joiners** (confirmed) — `totalOtherMembers` is derived from current `participant_ids.length`, not membership at message-send time. A member added after a message was sent will inflate the unread counter for that message. Consider capping unread count at the membership count at send time, or accepting this as a known UX trade-off.
4. **O(members x messages) rendering cost** (confirmed) — `Object.entries(readReceipts).filter(...)` runs for every own message in the viewport. In a 50-member room with 100 visible messages, that's 5,000 iterations per render. Consider memoizing or pre-computing the read counts.

## Batch member-add without transaction or size limit

The controller iterates over `account_ids` sequentially:

```ruby
account_ids.each do |account_id|
  account = Account.find(account_id)
  validate_no_blocks!(account)
  membership = @chat_room.dm_chat_room_accounts.find_or_initialize_by(account: account)
  membership.update!(accepted: false, left_at: nil)
end
```

There's no `ActiveRecord::Base.transaction` block, so if `validate_no_blocks!` raises on the third account, the first two memberships are already persisted. The client receives a 403/422 but two accounts were silently added — the frontend has no way to know which succeeded. Wrapping in a transaction would make the operation atomic.

`account_ids` has no upper bound. `params.permit(account_ids: [])` accepts any array size Rails will parse. A malicious client can send 10,000 IDs, each triggering `Account.find` (a primary key lookup), `Block.where` (two queries), and `find_or_initialize_by` + `update!`. That's roughly 40,000 queries per request with no rate limit beyond the standard API throttle. Adding `raise Mastodon::ValidationError if account_ids.size > 20` (or similar) would cap the damage.

## Unread count semantics and rendering cost

The unread calculation:

```typescript
const totalOtherMembers = (room.participant_ids?.length ?? 1) - 1;
const readCount = Object.entries(readReceipts).filter(
  ([accountId, lastReadId]) =>
    accountId !== message.account_id &&
    lastReadId &&
    /^\d+$/.test(lastReadId) &&
    BigInt(lastReadId) >= BigInt(message.id),
).length;
unreadCount = totalOtherMembers - readCount;
```

`totalOtherMembers` uses the live participant list. If a member joins the room after a message was sent, that message's unread count increases because the new member hasn't "read" it yet. From the sender's perspective, messages they sent before someone joined now show a higher unread number than the audience that actually could have seen them.

The `Object.entries(readReceipts).filter(...)` call runs inside the `.map()` over all messages. For a group of N members viewing M messages, that's O(N x M) per render. At 50 members and 200 messages that's 10,000 filter iterations per render cycle. Pre-computing a sorted receipt list or memoizing per-message counts would eliminate the repeated work.
