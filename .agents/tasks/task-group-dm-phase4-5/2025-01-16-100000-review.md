# Phase 4-5: Chat room creation, migration worker, streaming enhancements, and mobile UX

This change adds five capabilities to the Group DM system: a modal for creating new chat rooms with user search, an unread badge and sound notification in the navigation sidebar, optimistic message sending with pending/failed states, a background worker that migrates legacy `AccountConversation` data into the new DM tables, and block-relationship enforcement in the streaming push worker. The approach is feature-additive — no existing tables or APIs are modified, new behavior lives in the `/api/v1/dm/` namespace and the frontend DM feature tree.

**Watch for:** The migration worker fires `after_create` callbacks on every migrated message, which enqueues `PushDmMessageWorker` for each one — potentially flooding streaming channels and sending spurious notifications during bulk migration (confirmed). The unread count cache can drift stale because the cache invalidation strategy has a race: the count endpoint can write a stale value back to Redis after a concurrent invalidation (likely). The `dangerouslySetInnerHTML` usage for optimistic messages wraps user input in `<p>` tags client-side without sanitization, creating an XSS vector if the content contains HTML (confirmed).

## High-level view

The new chat room modal implements a self-contained search-and-select flow using the existing `v2/search` API, accumulates selections as tag chips, and creates the room by dispatching `createChatRoom` (now returning a Promise). The design isolates child components to satisfy Mastodon's strict ESLint rules around inline handlers and effect-based state.

The unread badge integrates into the navigation panel following the `NotificationsLink` pattern: a `DmLink` component fetches the count on mount, renders `IconWithBadge`, and the streaming handler increments for non-active rooms. Sound notification piggybacks on `meta: { sound: 'boop' }` through the existing sounds middleware.

The migration worker copies `AccountConversation` records into `DmChatRoom`/`DmMessage` rows with dedup via `status_id` uniqueness, triggered lazily on first DM page visit or in bulk via Rake. The critical risk is that `DmMessage.create!` triggers `push_to_streaming` per row — historical messages will be broadcast as if new.

Block enforcement in `PushDmMessageWorker` queries both directions of the Block relationship and skips streaming for blocked pairs. However, block checks only happen at streaming time, not at send time or REST fetch — so blocked messages are still stored and visible on page load.

The unread count endpoint uses a Redis cache with 60-second TTL, invalidated on new messages and mark-as-read. A read-modify-write race exists between the count endpoint and concurrent invalidations.

<summary>Issues (8)</summary>

1. **Migration triggers streaming callbacks** — `DmMessage.create!` in the migration worker fires `push_to_streaming`, enqueueing `PushDmMessageWorker` for every historical message. Suppress callbacks during migration or use `insert_all`. (confirmed)
2. **Optimistic message XSS** — The reducer wraps user content in `<p>${content}</p>` without escaping. If a user types `<img src=x onerror=alert(1)>`, it renders via `dangerouslySetInnerHTML` before the server-sanitized version replaces it. Escape HTML entities in the optimistic path. (confirmed)
3. **Unread cache race condition** — If the count endpoint queries the DB, then a new message deletes the cache key, then the endpoint writes its (now-stale) result back, the cache holds an undercount until TTL expiry. Use `SETNX` or accept the 60-second window. (likely)
4. **No retry mechanism for failed optimistic messages** — The UI shows "Tap to retry" on failed messages but no click handler is wired up. The failed state is terminal. (confirmed)
5. **Migration worker N+1 on status.media_attachments** — `statuses.each { |s| s.media_attachments.any? }` loads attachments lazily per status. Add `.includes(:media_attachments)` to the status query. (confirmed)
6. **Redis key for migration never expires** — `dm:migrated:{account_id}` is set permanently. If migration needs to be re-run, there's no way to clear it short of manual Redis intervention. Consider a versioned key. (likely)
7. **DmLink has no active icon variant** — `NotificationsLink` passes both `icon` and `activeIcon` to `ColumnLink`. `DmLink` only passes `icon`, so the nav item won't visually distinguish its active state. (confirmed)
8. **Rake task `migration_status` creates its own Redis connection** — It instantiates `Redis.new(url: ...)` instead of using `Redisable` or `RedisConfiguration`. This bypasses connection pooling and may use wrong credentials in Sentinel environments. (confirmed)

## Migration worker callback side effects

The migration worker creates `DmMessage` records using `room.dm_messages.create!`, which triggers all `after_create` callbacks:

```ruby
after_create :update_room_timestamp
after_create :mark_others_unread
after_create :push_to_streaming
```

For a conversation with 50 historical messages, this means 50 calls to `PushDmMessageWorker.perform_async`, broadcasting each old message to online room members as if it just arrived. The streaming handler dispatches `DM_MESSAGE_RECEIVED` with `meta: { sound: 'boop' }` for non-active rooms — migrating an account with many conversations triggers dozens of notification sounds in rapid succession.

The `mark_others_unread` callback also deletes the Redis unread cache key N times and sets `unread: true` on memberships repeatedly. The `update_room_timestamp` callback sets `last_message_at` to each old message's `created_at`, producing N unnecessary UPDATE queries before the explicit final correction at the end of `migrate_messages`.

Fix: suppress callbacks during migration (use `insert_all` for bulk creation followed by a single timestamp update) or add a guard condition on the callbacks that checks for a migration context.

## Optimistic message content injection

The reducer constructs optimistic messages by interpolating raw user input:

```typescript
content: `<p>${content}</p>`,
```

`MessageItem` renders via `dangerouslySetInnerHTML={{ __html: message.content }}`. Between send and server response, unescaped content is live in the DOM. `<script>` tags won't execute (innerHTML behavior), but `<img onerror>`, `<svg onload>`, and CSS injection via `<style>` tags will. Self-XSS in the basic case, exploitable if message drafts are shared or paste events inject HTML.

The server-side path properly escapes via `ERB::Util.html_escape`. The optimistic path needs equivalent escaping — a `textContent`-based escape function or the existing `escapeHtml` utility.

## Block enforcement asymmetry

The block check happens at streaming time only. A message from a blocked user is still stored in `dm_messages` and visible to the blocked party via the REST API (message list fetch). The streaming filter prevents real-time delivery but doesn't prevent reading the message on next page load. In a group room with N participants, the worker makes 2 queries (one per direction) regardless of group size, which scales well — but the incomplete enforcement means blocks reduce nuisance without providing full content isolation.

## Mobile panel switching — missing animations

The implementation uses CSS class toggling (`dm-panel-left--hidden-mobile`, `dm-panel-right--hidden-mobile`) with `display: none` at mobile breakpoints. The `transform:translateX` slide animations specified in the acceptance criteria (FEAT-003) are not implemented — the SCSS defines skeleton shimmer animations but no `slide-left`/`slide-right` transition classes. Panels appear/disappear instantly rather than animating.

## New chat room modal — fragile type assertion

The `createChatRoom` action returns a Promise through Redux-thunk, but TypeScript can't infer the return type through `dispatch()`. The modal uses:

```typescript
void (dispatch(createChatRoom({ account_ids: accountIds, title })) as unknown as Promise<{ id: string }>)
  .then((data) => { ... })
```

This double-cast (`unknown` then `Promise`) will silently break at runtime if the action's return shape changes. A typed `createAsyncThunk` or explicit generic on `dispatch` would be more robust.
